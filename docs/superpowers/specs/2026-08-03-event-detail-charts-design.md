# 異常事件詳細頁：從「全站流量」改為「對象視角」

日期：2026-08-03
狀態：已核准，實作中

## 問題

事件詳細頁唯一的圖表（`routes._event_trend()`）畫的是**整個資料來源的總量**，
與事件對象無關。圖下方的說明有寫「非僅該異常對象的請求量」，但那不足以阻止誤讀。

實際發生的誤讀（EVT-0004，`122.116.161.191 · Api2/RecoverTrans`，R03）：
圖上實際值 12–20 萬、同時段基線 median 39–58 萬，於是看圖的人得到
「量比平常低，所以沒事」的結論 —— 而圖上沒有任何一個像素跟那個對象有關。

`api/drilldown.py:236-239` 的註解早就記下這個缺口：

> 事件頁的趨勢圖是**整個資料來源**的量…**該對象自己的時序正是事件頁結構上給不出的東西**

這一頁要能在三秒內回答三件事：這個對象怪在哪、跟其他對象差多少、它的趨勢往哪走。

## 前置修正：R03 的基線與 metric 不是同一個單位

**這是本設計的阻擋項** —— 沒修好之前，「跟母體比」的面板會用可信的圖表傳達錯的結論。

R03 的 metric 是每 **(來源 IP × endpoint)** 每 60 分鐘（YAML `GROUP BY src, endpoint`），
但門檻讀的 `api_src_60m` 在 `calibrate.py` 是每 **(來源 IP)** 每 60 分鐘、
跨全部 endpoint 算的（`GROUP BY src, b`）。同一時段實測差 26 倍：

| 單位 | median | P95 | P99 | 樣本 |
|---|---|---|---|---|
| `api_src_60m`（規則實際在用，per src） | 7 | 86 | 2,835 | 141,616 |
| per (src, endpoint)（metric 真正的單位） | 2 | 20 | 109 | 6,067 |

三個後果，都是靜靜發生的：

1. **門檻系統性偏高、長期漏抓。** 門檻是 `p99 × 3`：錯的單位給 8,505，
   正確單位給 327（會被 `static_floor` 接手）。EVT-0004 的 6,480 在今天的基線下
   根本不會觸發 —— 它只是因為 production 基線還停在舊值（P99 2024 → 門檻 6,073）
   才叫出來。同一個行為，叫或不叫取決於基線抖動。
2. **事件頁的「資料限制」在陳述錯的母體。** `engine._eval_sql_threshold()` 由
   `base` 組出 `baseline_note`，所以畫面寫的 median/P95/P99 是 per-src 的分布，
   比真值高一個數量級，而使用者拿它當同儕比較的依據。
3. 用正確單位算，EVT-0004 是 P99（109）的 **59 倍**、median（2）的 3,240 倍；
   用現在的基線算，它只是「超過門檻 6.7%」的邊緣案例。**同一筆資料，相反的結論。**

這與 CLAUDE.md 已記載的「分桶與基線粒度必須成對」是同一類錯誤，
只是錯在**對象維度**而非時間維度。

修正順序（不可顛倒，照 CLAUDE.md「新增規則的完整路徑」）：

1. `calibrate.py` 加 `api_src_ep_60m`（`GROUP BY src, endpoint, hour`）
2. 重跑 `calibrate`
3. `replay` 回測，重新決定 `static_floor`（新門檻會大幅下降，R03 會變吵）
4. 才改 R03 YAML 的 `baseline_key`（該欄位在 UI 是唯讀的，只能改檔案）

## 頁面新結構

```
判讀列（4 個 stat tile，不是圖）
A. 對象自己的時序（主圖，28 天）
B. 母體位置          C. 24 小時作息
D. 端點來源集中度     E. 全站流量（降級）
```

### 判讀列

四個決定性的數字，刻意不畫成圖（dataviz：有時候答案不是圖表）。
以 EVT-0004 為例的實測值：

| 卡 | 值 | 說什麼 |
|---|---|---|
| 母體位置 | #2 / 6,067，P99 的 59 倍 | 同單位同儕裡排第二 |
| 端點壟斷 | 97.4%（近 7 天） | 這個 endpoint 幾乎只有它在打 |
| 作息擺幅 | 1.25×（全站 13.7×） | 沒有日夜節律 |
| 存在多久 | 28 天+，4,440 → 6,480（+46%） | 不是新事件，是長期程式在爬升 |

第四張卡最重要：它直接否定頁首「開始：2026-08-03 10:05」的敘事。

### A. 對象自己的時序（主圖）

- 折線 + `rangeArea` 逐 bucket 的自身 28 天同時段 median 帶 + 門檻水平線
  + 事件區間（`first_seen`..`last_seen`）塗色
- 帶與 median 由**同一趟查詢**的結果在 Python 端算，不進 `calibrate`
  （不需要新 baseline key、不需要每日重算）
- 成本實測 **14.7 秒**（最壞情況：`api` 表 + 從 headers 解析 IP）。
  這是全頁唯一慢的一塊 → **獨立端點 + 前端延後載入**，其餘面板先畫出來
- 端點必須是同步 `def`（不是 `async def`）—— 14.7 秒的阻塞查詢放進事件迴圈
  會把五分鐘排程一起卡住，與掃描端點踩過的是同一個坑

### B. 母體位置

- 橫向排名條：本小時 top 12 個同單位對象，本事件對象高亮；
  median / P95 / P99 / 實際門檻畫成參考線
- **對數軸**（2 → 9,877 跨 3.7 個數量級，線性軸下 median 那格是 0 像素）
- 顏色：其餘中性灰，只有本對象用 accent。這是「誰是主角」的**身份**編碼，
  不是排名編碼 —— 換一小時重畫，其他條不因名次變動而改色
- 底下必須寫「本小時共 N 個對象，中位數 M 次」。少了它，
  看的人不知道 top 12 是從多大的池子挑出來的
- 成本實測 0.2 秒
- **依賴前置修正**，否則參考線會畫在 median 7 / P95 86 上

### C. 24 小時作息

- 兩條線，各自佔**自身總量**的百分比（同單位、單軸；不是雙軸）
- 實測：對象 00:00–19:00 每小時都是 4.29%（24 小時均勻 = 4.17%）；
  全站從 04:00 的 0.69% 到 12:00 的 9.49%
- 全頁最一眼的圖：一條水平線疊在明顯的日夜波上，不需說明就看得出「不睡覺」
- 兩條序列 → legend 必須存在，並直接標註線末端
- 成本實測 1.4 秒

### D. 端點來源集中度

- 近 7 天該 endpoint 的來源佔比，top 6 橫條（實測 97.4% / 0.9% / 0.5% / 0.3%…）
- 回答「這個 endpoint 本來就這樣，還是被這個來源壟斷」
- 只在事件 entity 含 endpoint 維度時出現
- 成本實測 1.5 秒

### E. 全站流量（保留但降級）

沿用現有查詢，縮成小面板，標題明寫「全站 API Log（非本對象）」。
它的工作從「呈現這個事件」改成「呈現監測環境是否正常」。

**一併加「全站量異常偏低」警示**：實際值連續低於基線 median 一定比例時顯示 pill。
目前沒有任何規則會對「量掉一半」告警（R12 只看新鮮度，資料有進來、只是變少），
所有規則的靈敏度因此被同步稀釋，而且完全靜默。實測全站 API 日量：
7/30 331 萬 → 7/31 235 萬 → 8/1 132 萬 → 8/2 127 萬，8/1 起穩定在原本的 4 成。
不是週末效應：7/25、7/26 那個週末是全月最高（417 萬 / 399 萬）。

## 降級規則

「沒有資料」不可以呈現成「沒有異常」。

| 情況 | 行為 |
|---|---|
| R09（entity 是字面常數 scope）、R12（無 entity） | A/B/C/D 全部不出現，明寫「此規則沒有可追蹤的對象」；**不可**退回畫全站圖假裝有內容 |
| 規則沒有 endpoint 維度（R01、R07B） | D 不出現 |
| 對象 28 天內沒有歷史 | A 的帶留 `None` 不畫，**不補 0** |
| 母體基線缺該粒度 | B 的參考線不畫，明寫「無同儕分布可比」 |

對象 → ClickHouse 篩選條件的推導**沿用 `drilldown.py` 既有的 `_FILTER_BY_FP` /
`_FILTER_BY_COL`**，不新建第二份對照表 —— 那已是唯一真相，
且 `tests/test_event_drilldown.py` 在守它。

## 既有硬性約束（本設計已內含）

- 只經 `charts/ApexChart.js` 建圖；`options` 與資料數值無關，靠 `signature` 控制
  `updateOptions`
- 不用 `chart.group`（會把 `updateOptions` 廣播給整組、tooltip 互相覆蓋）
- 時間軸固定 `category` + 後端格式化好的標籤字串（`create_time` 是台北牆鐘）
- y 軸用 `yaxis.max: niceMax`，不用 `forceNiceScale + tickAmount`
- tooltip 一律經 `charts/tooltip.js` 組 DOM（endpoint 與品牌名來自
  ClickHouse／MySQL，字串拼接就是 XSS）
- 顏色只能取 `--chart-*` token。B 若需要新的高亮色，
  **必須重跑 `app.css` 註解裡的 dataviz validator**

## 砍掉的候選

**每分鐘節奏規律度（變異係數 CV）。** 原本假設「規律 = 機器」，實測後推翻：

```
本對象 CV = 0.193    全站 CV = 0.047    同 endpoint 其他來源 CV = 0.536
```

全站聚合比對象更平滑（大數法則），CV 高低完全無法區分機器與人。
留著只會做出一個看似有洞見、實際導向錯誤結論的面板。

## 實作順序

1. 修 R03 基線單位 + `replay` 回測重定 `static_floor`（B 的正確性依賴它，
   而且它本身就是長期漏抓）
2. 判讀列 + C + D（都在 2 秒內，不動 schema，先讓頁面「一進來就看得出來」）
3. B（等 1 完成）
4. A（獨立端點 + 延後載入 + 同步 `def`）
5. E 降級 + 全站量偏低警示

做完 2 就解決原始問題：現在進頁面看到的是全站流量，
做完後看到的是「這個對象不睡覺、而且壟斷了這個 endpoint 97.4%」。
