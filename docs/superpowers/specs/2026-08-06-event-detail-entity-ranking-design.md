# 事件詳細頁的對象面板改版：母體排名 + 對象拆解 + 對象趨勢

日期：2026-08-06
範圍：`web/components/entity-panels.js`、`src/console/queries/entity.py`、
`src/console/queries/entity_history.py`、`src/console/core/masking.py`、
`src/console/api/routes.py`

## 為什麼

`GET /events/{evt}/entity` 目前給三塊面板（母體位置、24 小時作息、端點來源集中度）。
實際使用時的問題有三個：

1. **母體位置的圖與它下方的表格是同一份資料**。表格逐列寫 label + count，
   而圖上每根長條 hover 就有同樣的數字 —— 一塊面板兩份相同內容，佔掉的高度
   讓「作息」被擠到右邊只剩半個寬度。
2. **排名看得到誰異常，但看不出那個異常長什麼樣**。看到「第 1 名 9,877 筆」
   之後的下一個問題永遠是「它在打什麼 endpoint、用哪個帳號、影響哪些品牌、
   這個量是持續的還是剛冒出來的」，而這一頁答不出來 —— 只能複製值跳去 Explorer
   重查一輪。
3. **排名只能看本事件的對象**。實際調查時最有價值的往往是「排在我前面那幾名
   是誰」，而現有面板只把本對象上色，沒有任何方式往下看其他列。

## 改完之後的版面

`entity-panels.js` 由「兩欄並排」改成四塊全寬、由上到下：

```
┌─ 對象判讀（四個數字磚，內容完全不動）───────────────────────┐
├─ 母體排名 · 對象拆解（全寬，內部左右兩欄）───────────────────┤
│ 母體位置（前 12 名）      │ 1.2.3.4 · Api2/GetProfile        │
│ ▓▓▓▓▓▓▓▓ 1.2.3.4…       │ 母體第 3 名 · 9,877 筆 [本事件對象]│
│ ▓▓▓▓ 5.6.7.8…           │ [1h][3h][12h][24h][3d][7d]        │
│ ▓▓ …                     │ ╱╲╱‾╲ 本期（實線）                │
│                          │ ┈┈┈┈ 前一個等長區間（虛線）       │
├──────────────────────────────────────────────────────────────┤
│ 拆解：[Endpoint] [帳號] [品牌] [分店]  ← 四張小橫條圖並排      │
└──────────────────────────────────────────────────────────────┘
├─ 24 小時作息（全寬，內容完全不動）─────────────────────────┤
├─ 端點來源集中度（全寬，內容完全不動）───────────────────────┤
```

左右兩欄用 `repeat(auto-fit,minmax(360px,1fr))`，窄畫面自動疊成一欄
（同這個檔案既有的做法）。

**右欄與拆解列永遠只在講一個對象**：預設是本事件的對象，點左欄任一長條就換成
那一列。刻意不做「預設空狀態」——兩種模式會讓「右邊在講誰」變成每次都要重新
確認的問題，而右欄的數字被誤讀成事件的數字正是這一頁上一次改版要消滅的缺陷。

## 一、移除母體位置圖下方的表格

刪掉 peers `ApexChart` 後面那張 `<table>`。連帶要改的兩處：

- `aria-label` 目前寫「精確數值見下方表格」，表格拿掉後那句話是謊言，改成指向
  tooltip。
- **取捨要寫下來**：那張表原本是這塊面板唯一能被螢幕閱讀器讀出精確值的形式
  （圖是 `dataLabels: false`）。移除後精確值只剩 hover tooltip 與 x 軸刻度。
  右欄上方的 `<select>`（見第六節）保留了「用鍵盤選到第 N 名」這件事，
  但它給的是名稱，不是數值。

`charts/bar.js` 的註解寫「精確值由 hover tooltip、x 軸刻度與下方表格三處提供」
—— 那句話對其他呼叫端（總覽風險排名、Explorer 排名）仍然成立，所以**不改
`bar.js`**，這個面板的例外寫在 `entity-panels.js` 的註解裡。

## 二、可點性與洩漏面（`masking.echoable`）

點一列 → 要把「那一列是誰」送回後端，也就是把原始值回送。兩種值不可以回送：

- `auth` 的 actor 是 **API token**，畫面上是 `token_XXXX` 指紋。回送等於用主控台
  把不可逆的東西還原。
- `masking.actor()` 對**超長帳號名**會截斷並附 HMAC 摘要，那也是不可逆的。

所以判定不可以寫成一份「哪些種類是單向的」靜態清單 —— `actor` 是否單向取決於
**值的長度**，靜態清單一定會漂移，而漂移的方向是「靜靜地把指紋當原值送出去」。

`core/masking.py` 新增：

```python
def echoable(kind: str | None, value: str) -> bool:
    """這個原始值的對外呈現是否等於它本身。

    True 表示回傳原始值不會多洩漏任何東西（IP、endpoint、品牌編號、
    一般長度的帳號名都是這種）。False 表示呈現是單向的
    （API token 的指紋、超長帳號名的 HMAC 截斷），原始值一律不可回送。

    **用執行期比對，不是靜態的「哪些 kind 是單向的」清單** ——
    `actor` 是否單向取決於帳號長度，清單會漂移，而漂移的症狀是
    把指紋當原值送出去。
    """
```

`peers.top[]` 逐列多一個 `keys`：全部維度都 `echoable` 時是原始值陣列，否則
`None`。`keys` 為 `None` 的長條點不動，畫面說出原因（不是壞掉，是那個值無法反查）。

`tests/test_masking_audit.py` 加一條：`/entity` 回應裡不得出現原始 token 樣式，
且 `keys` 存在時每一個元素必須等於同一列 label 對應的顯示值。

## 三、右欄：對象趨勢

### 錨點是事件的 `last_seen`，不是 `now()`

「過去 24 小時」是往**事件那個時刻**回推。用 `now()` 的話同一個事件在隔天會變成
一張與它無關的圖，而且不會有任何錯誤。畫面上固定寫
「截至 2026-08-05 14:00（事件最後出現）」——不寫的話一定被讀成「現在往前 24 小時」。

### 「前一個同時期」= 緊接在前的等長區間

24h → 前一個 24h；3d → 前一個 3d。六個區間統一規則、沒有特例。
虛線的每一點在 tooltip 裡帶**自己的真實時刻**，否則前期那條線上的點沒有時間可讀。

前期完全沒有活動時仍然畫那條 0 線，並加一句「前一個等長區間內這個對象沒有任何
活動」—— 那是有意義的訊號（這個對象是新的），把它隱藏起來才是把資訊丟掉。

### 分桶階梯自己一份，刻意不共用 `trends.BUCKET_LADDER`

`trends.BUCKET_LADDER` 的每一格都必須出現在 `calibrate.GRANULARITIES` 裡
（`tests/test_trend_buckets.py` 擋著），因為那個階梯的比較基準是 calibrate 算好的
`baselines`。這裡的比較基準是**同一趟查詢現算的前期**，沒有那個耦合 ——
同 `entity_history` 的自身基線帶。

取的分桶值仍是既有的 5/10/30/120，**不引入新粒度**：

| 區間 | 分桶 | 點數 |
|---|---|---|
| 1h | 5m | 12 |
| 3h | 10m | 18 |
| 12h | 30m | 24 |
| 24h | 30m | 48 |
| 3d | 120m | 36 |
| 7d | 120m | 84 |

每一格都整除，所以「往回位移一個區間長度」之後 `toStartOfInterval`
（原點 1970-01-01）仍然對齊。**用測試以行為驗證這件事** —— 錯一格不會報錯，
只會讓前期那條線整條錯位，而畫面完全正常。

### 一趟查詢覆蓋兩個區間

查 `[前期起, 本期止]` 再在 Python 切開：兩個區間的分桶天生一致，round trip 減半。
三條既有硬性約束照舊：

- 左界走 `timewin.align_bucket()`，**不是 `align_tick()`**（120 分鐘桶會差一格，
  zero-fill 的查表全部落空、整張圖靜靜變成一條 0）。
- 零填到整個區間，右界不超過 `timewin.effective_now()`（截短了就回 `window_note`
  說出來）。
- 零填後 `rows` 永遠非空，所以「有沒有活動」只能問 `total`。

### 實作位置

`queries/entity_history.py` 已經是「對象自己的時序」的家，新增
`recent_trend(ref, anchor, minutes)`。

## 四、拆解列：四個維度

拆解維度 = `endpoint、actor、brand、store` **減掉**已經被拿去排序的維度
（`ref.dims` 的 field），且該表支援（`explorer.entity_meta(field, source)` 非 None）。

- R03（src × endpoint）→ 帳號、品牌、分店
- R08（只有 src）→ Endpoint、帳號、品牌、分店

順序固定成「打什麼 → 誰 → 影響誰」（endpoint、actor、brand、store），
同一條規則的事件每次讀起來都一樣。全部維度都被用掉時回空清單 + 一句說明。

**時間窗與左欄完全相同**（規則的 `window_minutes`），所以左邊那根長條的長度
等於右邊各維度的總和。拆解**不吃 `minutes`** 就是為了維持這個對帳關係。

每個維度回 `groups`（相異值個數）、`blank`（該維度是空字串的筆數）、逐列 `share`。

**`blank` 一定要回**：前 6 名的佔比加不到 100% 時，畫面要說得出剩下的去哪了。
不回的話「沒有帳號的那些筆」會靜靜藏在分母裡。

品牌的 `_brand` 有兩個哨兵值（`-1` 品牌層級操作、`0` 未填），排名裡出現時
**照實列出並加註**，不過濾 —— 過濾等於偷偷改分母。

查詢數 = **1 + 維度數（≤ 5 支）**：一支把 `count()` 與每個維度的 `uniqExact`
與 `countIf(<expr> = '')` 一次算完（欄位別名是程式產生的常數 `g0`/`b0`，
運算式來自 `GROUP_BY`，沒有注入面），剩下每個維度一支 top-N。
條件是「單一 IP + endpoint 在 60 分鐘內」，非常選擇性。

## 五、端點

兩支都是**同步 `def`**（裡面的 ClickHouse 查詢是阻塞的，`async def` 會佔住事件
迴圈、連五分鐘排程一起卡住），都共用 `_entity_context()` 的守門
（含 `unresolved_reason()` 那道執行期檢查）。

### `GET /events/{evt}/entity/trend?minutes=1440[&v=…&v=…]`

- `v` **省略 = 本事件的對象**。所以預設載入不依賴可回送性（本事件的對象可能
  根本不在前 12 名裡，那時前端手上沒有 `keys`）。
- `minutes` 不在那六個值裡一律 **400**。「值不存在」與「這段時間沒有活動」
  必須分得開。
- 回 `{supported, label, is_self, anchor, minutes, bucket_minutes, total,
  prev_total, rows: [{bucket, count, prev_count, prev_bucket}], window_note}`。

### `GET /events/{evt}/entity/breakdown[?v=…&v=…]`

- 同上的 `v` 語意。
- `v` 的個數與 `ref.dims` 不符一律 **400** —— 少一個就是在查一個範圍更大的對象，
  數字會比左邊的長條大而且不報錯。
- 比對不到任何記錄時回誠實的空狀態 + 原因，不回空陣列裝作查過了。

### `GET /events/{evt}/entity`（既有）

回應多一個逐列的 `peers.top[].keys`（見第二節）。**不多跑任何查詢**，
所以既有那約 3 秒不變。

## 六、前端行為

- 右欄與拆解列的狀態是「目前選中的對象」，前端以 `keys.join(' ')` 為鍵
  快取拆解結果與各區間的趨勢，點回來不重查。
- 長條點擊走 ApexCharts 的 `chart.events.dataPointSelection`，handler 從
  非響應式的 `this._peerRows` 持有者讀那一列（同 `tooltip.custom` 的契約）——
  `options` 因此仍然與資料數值無關，`signature` 不必因為選取而變。
- **鍵盤可用**：右欄上方一個 `<select>` 列出那 12 名，同時當「現在看的是哪一列」
  的指示器。長條點擊不是鍵盤可達的，而移除表格之後這是唯一還能不靠滑鼠選到
  第 7 名的方式。
- 區間切換走既有的 `components/range-picker.js`，presets 是那六個值。
  **不給自訂絕對區間** —— 錨點是事件的 `last_seen`，自訂絕對區間會讓這張圖
  與事件脫鉤（要那個就去 Explorer）。
- 換事件（`evtNo` watch）時清掉選取與兩份快取，退回本事件的對象。

## 七、成本

`api` 表的來源 IP 要對 `headers` 做 JSONExtract。選 7d 時趨勢的查詢範圍是
**14 天**（本期 + 前期）；參照既有實測（`entity_history` 28 天 5–7 秒），
預估 3–4 秒，而且只在使用者主動切到 7d 時發生。預設 24h 是 2 天。

實作時實測並把數字寫進註解。若 7d 真的超過 10 秒，就**在該選項旁標示「較慢」**，
不偷偷降級成別的區間 —— 使用者選了 7d 卻拿到 3d 的圖是最糟的結果。

## 八、測試

新增／增補：

- `tests/test_event_entity.py`
  - `keys` 的可回送性：一般帳號與 IP 有 `keys`；`auth` 的 actor（token）沒有。
  - `v` 個數不符 → 400；`minutes` 不在封閉集合 → 400。
  - `v` 省略時的對象等於本事件的對象（`total` 等於 `peers.own`）。
  - 拆解的 `share` 與 `blank` 對帳：`sum(rows.count) + blank <= total`，
    且 `groups >= len(rows)`。
  - 拆解不含已經被拿去排序的維度。
- 新檔 `tests/test_entity_recent_trend.py`
  - 六個區間的 (區間, 分桶) 都整除，且位移一個區間長度後分桶仍對齊
    （**行為驗證**：本期第一個 bucket 與前期第一個 bucket 的時間差
    等於區間長度）。
  - 零填：`len(rows) == minutes / bucket_minutes`，且相鄰 bucket 的間隔固定。
  - 前期無資料時 `prev_total == 0` 且仍然有 `rows[].prev_count`。
- `tests/test_masking_audit.py`
  - `/entity` 回應不得出現原始 token 樣式；`keys` 存在時等於顯示值。

## 九、明確不做

- **不動 24 小時作息面板**（使用者 2026-08-06 決定）。它只是從右半欄移到下方
  全寬，內容、查詢、區間都不變。
- 不動端點來源集中度。
- 不做拆解列的第二層下鑽（點品牌再往下拆）。一層已經回答「問題在哪一塊」，
  再往下就是 Explorer 的工作。
- 不給趨勢圖自訂絕對區間（見第六節）。
- 拆解維度就是 `endpoint / actor / brand / store` 這四個，不另外加新維度。
